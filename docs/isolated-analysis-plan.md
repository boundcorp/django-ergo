# Isolated analysis workspaces

Status: disabled implementation for review, **not provisioned, deployed or runtime-validated**. Draft PR: https://github.com/boundcorp/django-ergo/pull/408 . No paid inference calls, infrastructure changes or deploys are part of this change.

## Shipped code

`plugins/analysis_service.py` and `plugins/analysis.py` implement seven opt-in tools: Python submission, status/cancel, bounded file listing, attachment import/export, dataset open and structured select. No session lifecycle hook provisions anything. Only first tool use with `ERGO_ANALYSIS_ENABLED=True` creates a workspace receipt, and only submission/transfer creates a controller record/PVC. Disabled configuration raises before database allocation. The old `analysis.runner.execute` contract remains intentionally fail closed; it is not a second execution path.

Migration `0064_isolated_analysis` adds lazy session workspace receipts (one active workspace/session), async job receipts and versioned dataset handles. Every app operation reloads the session/user relationship, applies `closed_to`, and scopes workspace/job/dataset lookup to that exact session. Even another session owned by the same user cannot use its handles. Imports reuse `AttachmentsPlugin.file_for`, including same-user cross-session and closed/private source restrictions. It additionally refuses **all** `private_export` copies, even destination-local copies, because allowing arbitrary transformations and untainted re-export would launder their no-forward restriction. Supporting derived protected outputs requires a separate provenance design; refusal is deliberate and tested. Shared-message exports follow the existing attachment copies' ownership; arbitrary source ids do not bypass those ACLs.

`analysis/client.py` is HTTPS-only, verifies certificates, ignores ambient proxy credentials, rejects redirects, bounds streaming response bytes and never starts processes. `analysis/protocol.py` signs canonical bounded JSON with HMAC-SHA256. Envelopes bind protocol version, timestamp and random nonce; replies bind the request nonce. The controller durably records consumed nonces before side effects and rejects replay. Every request includes workspace/session/user authorization claims from the trusted application, never from model arguments. A compromised application/key is in the trusted computing base; HMAC does not independently authenticate end users.

`analysis/controller.py` is a separately launched, single-replica trusted service with a SQLite WAL/FULL durable ledger on its own volume. It alone owns narrowly scoped Kubernetes credentials. The ledger binds workspace ids immutably to session/user, enforces one active job/workspace, records submission intent before launch and rejects reuse of a job id with different request bytes. App receipts preserve canonical submission bytes to retry ambiguous HTTP failures with the same job id. Backend errors retain durable fences. Deterministic pod names allow recovery after controller restart. Polling and the server's periodic reconciliation enforce a 90-second submission-to-reaping deadline, including pending pods; pods separately have a 60-second active deadline. Cancellation and timeout enter `reaping`; terminal results are released only after durable container termination evidence and observed pod absence. Every pod has `analysis.ergonaut.dev/termination-observed` as a finalizer. Graceful deletion initiates cancellation; the controller removes only its own finalizer using UID/resourceVersion-tested JSON Patch after committing kubelet container termination evidence. A terminal Pod phase alone (including synthetic NodeLost/ContainerStatusUnknown) is insufficient, and API disappearance alone never releases a fence. Missing ambiguous launches, unscheduled/unconfirmed pods and node loss can hold a fence indefinitely pending independently verified runtime/node fencing; operators must not manually remove finalizers or ledger fences while execution may survive. No automatic operator override is supplied. Cancellation before an uncertain submission arrived records a durable cancelled job tombstone so a delayed retry cannot launch it.

`analysis/kubernetes.py` is the actual Kubernetes adapter, not a mocked production runner. It creates one PVC/workspace and one ephemeral pod/job, requires a digest-pinned image and configured sandbox RuntimeClass/storage class, and mounts exactly that workspace PVC plus private bounded tmpfs. The controller never mounts user workspace storage. Job pods have no Kubernetes token, service links, credentials, runtime socket, host paths, privileged containers or host namespaces. They run as uid/gid 10001, read-only root, all capabilities dropped, no privilege escalation, RuntimeDefault seccomp. Only explicit request/library environment variables are set. Separate namespaces, enforced network denial, sandbox runtime, PID limits and quota-backed storage are mandatory **unprovisioned prerequisites**, not properties established by the Python code.

`analysis/executor.py` is the credential-free job entrypoint. Entrypoints use Python `-I` to exclude writable workspace imports and ambient Python paths. Arbitrary Python source enters the child over stdin rather than command-line arguments and runs inside the isolated pod, with bounded pipe capture and a 55-second child deadline. Its process group is killed; final pod termination reaps descendants that escaped the group. CSV, Parquet and XLSX parsing, pandas and DuckDB execution occur only in job pods, never in web, bot or Celery processes. The application/controller do not import the executor. Tests invoke it only with trusted local fixtures; those tests do not establish isolation. Arbitrary Python shares the executor UID but cannot reach the container log stream or forge the executor's log record (see "Container log isolation" below); it still controls its own output and workspace, so neither valid executor JSON nor a controller HMAC proves result truth. The application validates dataset schema/count bounds and select row/column/count/cursor consistency before creating receipts or signing cursors. It never interprets workspace data as application/controller code. Scientific correctness still requires appropriate review of inputs and scripts; forged, internally consistent results remain possible inside a malicious workspace.

Two real library skills, `data-analysis` and `calculations-and-scripting`, request the registered `analysis` plugin and teach concrete full-data filtering, grouped aggregates, cursor pagination, pandas joins, plotting, exporting and accurate failure reporting.

## Data contract and limits

Dataset open returns a generated Parquet snapshot, source row count and schema. Dataset ids map to a session workspace and SHA256 content version. Select checks that version on every query, so script modifications cannot silently mix cursor pages. Structured SQL accepts only schema-quoted identifiers, allowlisted aggregates/sort directions and parameter-bound predicate values. Predicates include eq/ne/lt/le/gt/ge/in/is_null/not_null/and/or/not, with bounded complexity, depth and scalar sizes. DuckDB disables external access, automatic extension installation/loading, unsigned/community extensions, and locks its configuration. Data is registered from an already parsed in-memory pandas frame; structured requests cannot supply SQL, paths, extension names or SQL functions. This is defense in depth inside a sandbox, not an SQL-only sandbox for arbitrary Python.

Queries apply filters/grouping/aggregation to the full dataset before paging. `total_rows` is the exact output row/group count, `source_rows` is the full source count, `count_kind=exact` and provenance describes scope. Failures never fall back to sampled aggregates or invented counts. Ordering includes all output columns after explicit sorting; identical projected rows are indistinguishable. Authenticated Django cursors bind workspace/dataset/version/query hash/offset and expire after 24 hours. Row and byte bounds both apply; oversized single rows error with advice to narrow projection. Float/decimal/date/complex cells are serialized as strings; schema retains their inferred types.

| Limit | Enforcement |
| --- | --- |
| One active job/workspace | Durable controller unique index; held through reaping |
| Transfer lease | Random session-authorized token, 5-minute renewable expiry, active jobs additionally fenced |
| Request/response envelope | 96 KiB canonical JSON; per-job request 64 KiB; reply request-nonce binding |
| Python source | 32 KiB checked inside job; total request also bounded |
| Python captured output | 48 KiB, explicit output-limit reason; serialized final result capped at 64 KiB |
| Structured output | Up to 1000 rows, 128 columns, approximately 44 KiB row JSON; final response byte cap |
| Predicate tree | Depth 8, 64 nodes, membership 100 values, string scalar 4096 bytes |
| File transfer | 16 KiB chunks; actual streamed total at most 64 MiB, independent of attachment metadata |
| CPU/RAM | Pod cgroups: one CPU / 512 MiB; DuckDB 256 MiB and one thread |
| Temporary files | Private memory-backed `/tmp`, 128 MiB sizeLimit, charged to memory cgroup |
| Persistent workspace | Dedicated 1 GiB PVC; **storage backend must enforce a hard filesystem/block quota** |
| PIDs | **Sandbox node kubelet podPidsLimit <=64 and runtime cgroup enforcement required**; no portable PodSpec PID field |
| Wall time | Python 55s, pod active deadline 60s, controller submission deadline 90s |
| Container logs | User code holds no handle on the container log; the executor writes one record of at most 64 KiB (see "Container log isolation") |
| Termination message | Kubelet-created host file, writable by the container: user code is capped at 64 MiB by `RLIMIT_FSIZE`, then the executor truncates it to a ~100-byte digest record |
| Ephemeral disk | Pod 256 MiB ephemeral storage is eviction-based, **not a hard disk quota**; the rootfs is read-only (gVisor `overlay2=root:memory` on Octo) |

No network is permitted, including DNS, Kubernetes, node/metadata endpoints or Internet. Kubernetes NetworkPolicy must be enforced by the selected CNI; a policy YAML is not proof. Sandbox/network adversarial tests must cover link-local, node IP, localhost behavior, IPv6 and metadata. No packages can be fetched at runtime. Container images must contain only reviewed dependencies/code, no source checkout credentials or environment files.

## Transfers and retention

Files use flat generated/safe names, reject absolute paths, separators, traversal, leading dot and NUL. Executor opens use `O_NOFOLLOW|O_NONBLOCK` and descriptor checks for regular files, one hard link and size caps. All jobs/transfer chunks serialize per workspace, preventing an arbitrary script from racing a privileged transfer. User scripts can modify their own workspace; they cannot mount another workspace or controller storage. Import creates a generated file using O_EXCL and validates contiguous offsets. Export validates chunk sizes, exact offsets, total size, stable content hash and a final end-to-end checksum, spooling bounded bytes to a temporary app file without parsing. Before every transfer action the app rechecks authorization, and every import chunk rechecks source attachment ACL, storage identity and update/version metadata. A streaming import SHA256 is checked against source metadata when available and returned as provenance. Exports are separate Django storage attachments, not paths pointing at workspace storage.

Each transfer chunk currently launches an isolated job. This is intentionally simple and safe but has substantial startup overhead for multi-megabyte files; no throughput benchmark is claimed. Transfer tools wait for those jobs, while calculation/query tools return asynchronous job receipts. An interruption can leave a partial import in its own workspace and a renewable lease that expires after five minutes; a running job keeps its stronger fence. No background parsing task can run eagerly in the app.

Controller reconciliation expires idle workspaces after `ANALYSIS_RETENTION_DAYS` (default 30), skipping active jobs and unexpired transfer leases. It commits a permanent ownership tombstone before deleting job results/PVCs, then retries storage deletion after crashes until a confirmed PVC absence, recording completion to avoid repeatedly deleting purged volumes. Kubernetes PVC deletion is asynchronous and requires an approved Delete reclaim policy; retained volumes/backups require their own deletion policy. `cleanup_analysis` reconciles app receipts only after the controller confirms retirement, preserving attachments and a workspace tombstone. Schedule this command daily in the host application with matching `ERGO_ANALYSIS_RETENTION_DAYS`; unknown/failed controller responses never authorize local deletion. New tool use retires an expired receipt and asks for retry to allocate a fresh workspace. App session deletion may leave controller data until normal expiry. Logs and backups must have a matching privacy/retention policy; this feature does not erase unrelated chat history or exported files.

## Container log isolation (blocker B7)

The kubelet on Octo rotates container logs (10 MiB x 5) periodically but has no hard quota, so a script that writes to the container's stdout could fill node disk between rotations. The fix is that no process running user code can write to the container log at all. `executor.main()`, as PID 1 of the job container:

1. closes every inherited descriptor above 2, moves the original stdout to one private close-on-exec descriptor and points 0/1/2 at `/dev/null`, so `/proc/1/fd/1`, `/dev/stdout` of PID 1 and anything printed by pandas/DuckDB go nowhere;
2. calls `prctl(PR_SET_DUMPABLE, 0)`. A non-dumpable process's `/proc/<pid>/fd`, `fdinfo`, `mem` and `environ` are unreadable to other processes of the same uid without `CAP_SYS_PTRACE` (which the pod drops), and `ptrace`/`pidfd_getfd` fail. The saved descriptor is therefore unreachable, including through `/proc/1/fd/<n>`;
3. before each Python job and each parse, runs a probe child as the same uid that tries to open `/proc/<parent>/fd/<saved>`. Only a permission error (EACCES/EPERM, what Linux and gVisor return) passes; if the open succeeds or fails any other way (no `/proc`, wrong pid), the job fails closed with `Container log isolation unavailable` and no user code or parser runs;
4. ignores SIGINT, the one signal Python handles by default, so a same-namespace process cannot raise `KeyboardInterrupt` inside PID 1 (children get the default back);
5. parses CSV/Parquet/XLSX in a forked child that closes the saved descriptor first, runs in its own session under the same rlimits and stays non-dumpable, and returns its JSON over a bounded pipe (errors are dropped, never logged). A parser exploit therefore gets no more than user Python;
6. runs user Python in a new session (no controlling terminal: `/dev/tty` is ENXIO; admission forbids `tty`, so there is no `/dev/console`), with fds 0/1/2 bound to bounded pipes, `close_fds`, `RLIMIT_FSIZE` = 64 MiB and no core dumps;
7. after the script or parse, kills (`kill(-1, SIGKILL)`) and reaps every other process in the pod, so escaped daemons cannot race the record, then writes one record of at most 64 KiB to the saved descriptor and overwrites `/dev/termination-log` with `{"v":1,"bytes":N,"sha256":...}` for that record.

The controller (`KubernetesRuntime.result`) accepts the log only if its length and SHA-256 match that termination message, so bytes that did not come from the executor are rejected even if some future runtime let them through.

Options considered: closing the log entirely and returning results only through the termination message is not possible, because the kubelet keeps at most 4096 bytes of it and results reach 64 KiB. Running the child under another uid or PID namespace needs capabilities that restricted PSA removes. A second "reporter" container would break the one-container admission shape. Non-dumpable PID 1 plus the runtime probe is the strongest option that works under gVisor runsc and restricted PSA. It was verified locally under gVisor release-20261102.0 (Octo's version, rootless `runsc do` as uid 10001 with PID 1 the executor): every `/proc/1/fd/*` open and listing, `/proc/1/mem` and `/proc/1/environ` returned EACCES, `/dev/tty` ENXIO, `/dev/console` ENOENT, the termination-file fill stopped at 64 MiB with EFBIG, a detached daemon was killed before the record, and the log was exactly the record. The same cases run in CI against the built image under runc and gVisor (`infra/analysis/smoke_test.py`; under Docker, gVisor lets the same uid list the fd numbers in `/proc/1/fd` but still refuses to open any of them, `mem` or `environ`) and as subprocess tests, including PID-1 variants in a PID namespace (`tests/test_analysis_log_isolation.py`).

Residual: user code (or a compromised parser) can still exploit a kernel or gVisor bug to defeat dumpability, and can still fill its own bounded outputs (64 MiB termination file, workspace PVC quota, `/tmp` tmpfs). A log write it somehow achieved would fail the controller's digest check but would still consume node disk; kubelet rotation remains the backstop for that case.

Pod spec delta for infra-octo #337: the executor container now sets `terminationMessagePath: /dev/termination-log` and `terminationMessagePolicy: File` explicitly (both are the API defaults, so the defaulted object admission sees does not change). The `ergo-analysis-job-pod` VAP should pin them with `variables.c.terminationMessagePath == '/dev/termination-log' && variables.c.terminationMessagePolicy == 'File'`, because `FallbackToLogsOnError` or another path would weaken the digest check. The acceptance script's `log-fill` case is expected to pass (`/proc/1/fd/1` now fails with EACCES); its `results()` parser is unchanged because the log is still exactly one JSON record.

## Images

`.github/workflows/analysis-images.yml` ("Analysis images") builds `ghcr.io/boundcorp/ergo-analysis-runner` and `ghcr.io/boundcorp/ergo-analysis-controller` from `infra/analysis/*.Dockerfile`. The Python base is pinned by digest in `infra/analysis/base-images.env` and the Dockerfiles refuse an unpinned `PYTHON_BASE`. Dependencies come only from the hash-locked `infra/analysis/{runner,controller}.requirements.txt` (`pip --require-hashes --only-binary=:all:`), generated from the `.in` files, which `tests/test_analysis_images.py` keeps equal to the pyproject extras. The package itself installs with `--no-deps`, so Django is not in either image. The workflow runs on pull requests and main pushes that touch the analysis code. It runs the analysis tests, builds both images, smoke-tests the runner under runc and under gVisor (same release and SHA512 as Octo), and on main only pushes `sha-<commit>` tags and prints the resulting digests, plus the pinned nginx-unprivileged digest for the controller's TLS sidecar, in the job summary. There is no moving tag. It runs on GitHub-hosted runners because the gVisor step installs runsc into the runner's Docker. There is no dependency vulnerability scanner in this repository yet, so none runs. Adding one (for example `pip-audit` on the two locks, or a Trivy image scan) is a separate decision.

Copying a digest into infra-octo (admission `runnerImage`, deployment `ANALYSIS_IMAGE`, the controller image, nginx) is a reviewed commit there. The new GHCR packages are private by default, as `ergonaut` is; Octo must be able to pull them without `imagePullSecrets`, which admission forbids, through the same node-level registry credentials it uses for `ergonaut`, or the packages must be made public.

## Validation and known limits

Offline tests cover protocol authentication/replay/tampering/bounds, immutable job identity, session/user isolation, crash recovery, active/transfer cleanup fences, cancellation/timeout, pod security shape, parameterized query attacks, predicate/aggregate operations, CSV/Parquet/XLSX, exact counts, deterministic pages/version checks, path/symlink/hardlink attacks, streaming actual-size caps, attachment ACL reuse, independent exports, lazy/disabled behavior and real tool registration. Repository plugin/skill/attachment tests are run alongside these. Final results and commands are recorded in `artifacts/isolated-analysis-validation.md`.

Image builds and the container-log smoke tests run in CI (runc and gVisor, "Images" above). Real Kubernetes smoke tests and the full target-runtime adversarial suite are **unrun**. The implementation is usable through the proposed deployment but cannot be represented as currently isolated or enabled infrastructure. Known first-version limits: protected private-export copies cannot be imported, one controller replica, one job/workspace, whole-file pandas reads bounded by sandbox memory (large files can fail), first-sheet XLSX, no structured joins (pandas joins supported), offset pagination that recomputes full queries, inefficient per-chunk pod startup, no transfer progress/resume tool, no terminal-event notification (poll explicitly), and deployment-specific hard disk/PID/network controls. A serialized result exceeding its final envelope budget fails explicitly rather than silently returning a sample.

Reference semantics: [DuckDB security configuration](https://www.duckdb.org/docs/1.4/operations_manual/securing_duckdb/overview), [Kubernetes ephemeral-storage eviction limits](https://kubernetes.io/docs/concepts/storage/ephemeral-storage/), [Kubernetes PID limits](https://kubernetes.io/docs/concepts/policy/pid-limiting/). These explain defense-in-depth settings and why storage/PID enforcement requires approved runtime configuration.

## Independent security audit (2026-11-27)

The independent review of `1078084` found and fixed unsafe disappearance-based fence release, loss of termination evidence across controller crashes, writable-workspace import shadowing, malformed dataset/select trust at the application boundary, a mid-import private-export flag race, and cancellation of an uncertain pre-launch submission. It also found an actual import-layer test failure; the integration service now lives in the plugin layer. See `artifacts/isolated-analysis-security-review.md` for severity, code locations, evidence and residual gates.

Local HTTP harnesses exercise controller authentication and the installed generated Kubernetes client (37.0.3): PVC get/create/delete, Pod create/get/log/delete/patch, 404 deserialization, camelCase query parameters, JSON Patch media type and finalizer retention. These verify adapter wire semantics against an emulator; they do not verify Kubernetes admission, kubelet finalizer behavior, runtime process cleanup, CSI quota enforcement or TLS deployment. Target-runtime tests must validate finalizer preservation through deletion/node failure, reliable kubelet termination status, crash recovery and the operational fencing procedure. Do not enable until that separate acceptance succeeds. Kubernetes authorities: [Pod termination](https://kubernetes.io/docs/concepts/workloads/pods/pod-termination/), [Pod lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/), and [finalizers](https://kubernetes.io/docs/concepts/overview/working-with-objects/finalizers/).
