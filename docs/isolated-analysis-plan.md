# Isolated analysis workspaces: architecture and security plan

Status: design, not provisioned or production-ready.

## Repository findings

Bot tools are registered through `bots/tools.py` and plugins through `bots/plugins.py`; opt-in library skills live in `bots/skill_library/` and can request plugins. `plugins/attachments.py` implements same-user cross-session access with closed-session and private-export checks; shared files are represented through thread messages (`ergonaut/ergonaut/api/bots.py`). Attachment bytes use Django storage (`conversation/models.py` and `conversation/attachments.py`). Existing bash executes on the host and explicitly is not isolated (`plugins/bash.py`). Celery may run eagerly in process (`ergonaut/CLAUDE.md`); production workers use `ergonaut/infra/prod/start-celery-worker.sh`. `ergonaut/Dockerfile` packages the application, not a hostile-code runner.

## Boundary and implementation sequence

Use a separate, trusted controller as the only broker for per-job isolated containers; a queue is transport, not isolation. The app must fail closed with no controller and must never start a local process or mount a container runtime socket. The controller must authenticate job submissions, authorize opaque session-scoped workspace references, and independently enforce one ephemeral job with network completely denied (including cluster and metadata), non-root, no capabilities or privilege escalation, read-only root, no service account token or credentials, workspace-only writable storage, CPU, memory, ephemeral disk, PID, wall-clock and output limits. Cancellation, timeout and controller failure must terminate and reap every process before releasing the workspace lease. The container image must be pinned and include Python, pandas, DuckDB, plotting and required data readers; no arbitrary SQL or extension installation is exposed by a structured query API. No controller or infrastructure has been approved or provisioned.

Workspace records must be created lazily per session and user, with authorization checked on every operation; reuse the attachment plugin's access checks, including private exports and shared-message semantics. Transfer via bounded streams; never trust attachment names, MIME types, archive contents, symlinks or hardlinks. Storage needs isolated per-workspace paths or volumes and a safe, atomic lease around every job, transfer and cleanup. Retention defaults to 30 days and must reconcile database and storage after crashes without deleting active jobs; exports become independent attachments. Dataset handles bind owner, immutable dataset version and query; cursors are authenticated and bind query/version. Responses bound both bytes and rows and clearly distinguish exact counts from unknown counts. Parsing potentially hostile files belongs in the isolated job as well.

Before enabling, an infrastructure change requires separate review and approval for the controller, authenticated broker, image provenance, network enforcement, workspace storage isolation/quotas, scheduling, resource limits, observability and adversarial isolation tests on the target runtime. Containers share a kernel and shared-volume semantics remain residual risks; stronger sandbox runtimes or dedicated nodes may be required. No real isolation is established by unit tests or mocks.

## Current implementation and remaining work

The `django_ergo.analysis` package currently contains only a fail-closed runner stub, resource-limit validation, and a bounded parameterized predicate compiler. These components are not registered as bot tools, do not create a workspace or execute code, and are not an operational broker or security boundary. Tests exercise the stub and compiler in isolation; they do not prove isolation.

Still required: implement and review the authenticated controller protocol and actual executor; workspace/session ownership, lazy provisioning, bounded attachment transfer, active-job leases and crash-safe retention; isolated readers and query execution, versioned dataset handles, pagination and exact counts; bot tools and two skills; integration and real-runtime adversarial tests. No migration or rollout is included in this foundation. Infrastructure must remain disabled until those changes and the prerequisites above are reviewed and approved. Rolling back this foundation consists of reverting its commit; it changes no runtime behavior or stored data.
