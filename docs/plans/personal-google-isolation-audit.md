# Personal Google isolation: source audit and proposed boundary

Source-only audit, 2026-11-23. No account content, runtime configuration, secrets, logs, infrastructure, or private conversations were inspected. This repository alone cannot establish which Google credential or integration exists in production, its exact current path, or the behavior and permissions of other repositories or services.

## Findings

- `bots/model_choice.py` restricts an allowlisted private-pool bot's model tasks to that pool and denies subscription coding agents. This is a pool membership rule, distinct from a bot's `private: true` access control.
- Before this hardening, `ergonaut/api/bots.py:check_model`, `Bot.pick_model`, and `Bot.engine_spec` accepted public or auto chat selections for a private-pool bot. A persisted session override, retry route, or a non-API call could therefore send future context to a public provider. Private selector validation alone prevents unauthorized *use of a private pool*, not exfiltration *from* a private bot.
- `Bot.make_ancillary_engine` routes private-pool titles and compaction to the pool; browser tasks validate model choices and use `Bot.make_engine`. These paths still depend on central construction and on every other tool or integration respecting the boundary. `bash_review` explicitly excludes private-pool bots. A wider inventory of plugins, outbound tools, messaging, exports, logs and background jobs remains necessary before enabling Personal Google access.
- The browser documentation describes a shared browser profile; browser access to a signed-in Google account is not an account isolation mechanism. This audit did not inspect the browser, Google account, bot definitions outside this repository, or runtime state.
- A credential-only Google gateway can prevent other bots from directly obtaining Google credentials, but cannot isolate returned mail/calendar data once handed to a bot in a shared Ergonaut process or database. Chat history, context, summaries, tool outputs, memory, shared administrative access, other tools and operators may retain or expose results. Private inference routing is necessary but not sufficient.

## Options for later approval

1. **Credential boundary only:** a separate Google gateway service owns a dedicated OAuth client and Personal refresh token; a narrowly authenticated Personal-only caller gets allowlisted Gmail/Calendar operations. Proposed source: a newly authorized Personal-specific OAuth consent and refresh token, provisioned by an operator from a secret manager (existing credential location is unverified). Proposed gateway mount: `/run/secrets/personal-google/oauth-client.json` and `/run/secrets/personal-google/refresh-token`; the Ergonaut process receives neither. Gateway endpoint and caller identity must be designed and authorized before implementation. This protects credentials, not returned data in the shared runtime.
2. **Stronger data boundary:** dedicated Personal runtime and worker identity, separate database and object storage, isolated network policy and gateway identity, and separately protected memory; no shared browser profile or shared bot tools with access to Personal data. Define operator/admin access, backups, telemetry, retention, inter-bot communication and failure behavior explicitly. This is a design option, not a claim of complete isolation.

Neither option is provisioned or authorized by this audit. Before implementation, confirm the real credential source and exact storage/target paths, OAuth scopes, read/write operations, caller authentication, egress destinations, retention, administrator trust, and whether shared infrastructure is acceptable. No existing path or credentials were verified; the paths above are proposals, not discovered facts.

A failed providers reload previously discarded private-pool membership, so an old public session override could bypass pool enforcement. The hardening retains the last known membership with pools disabled on reload. On a fresh start with invalid or missing pool configuration there is no trustworthy membership list to recover: a bot explicitly configured with the reserved `personal` selector fails closed even with an existing public session override. Other unconfigured pool names and bots without an explicit private selector cannot be identified from missing configuration. Resolve that startup/configuration boundary and audit all persisted sessions before enabling private Google data; do not treat this PR as complete end-to-end isolation.
