## Overview

Django Ergo has two retrieval stores and two explicit indexing operations. Article retrieval searches persisted Article embeddings. Repository retrieval searches SourceUnits extracted from one committed Git snapshot. Neither path indexes content as a side effect of an ordinary Article save.

## Retrieval

`ArticleQuerySet` exposes content, summary, and weighted multi-field semantic searches. These methods operate on the queryset they receive, so tenant and knowledge-base scoping remains the caller's responsibility. They return Articles ranked by vector distance.

`search_repository` returns SourceUnit cards instead. It combines exact symbol/path matches, PostgreSQL lexical ranking, vector distance, and relation context, then applies optional role and kind filters. Its results retain the source path, structural symbol, content hash, and indexed commit.

## Indexing

`index_article` generates only the requested Article fields, checks vector dimensions, and saves the embedding fields inside a transaction with the managed-write guard explicitly enabled. Empty text produces a null embedding.

`index_repository_commit` reads `.ergo/index.yaml` from an allowed commit, extracts bounded Python or Markdown units, assigns stable file and unit identities, reuses unchanged embeddings for the same provider identity, rebuilds relations, removes stale index records, and advances the index checkpoint atomically.

## Concrete Flow

1. Application code calls `index_article(article, fields=("content", "summary"))`; later an already-scoped ArticleQuerySet performs semantic retrieval.
2. Independently, an operator runs repository indexing for an allowed commit. The index contains SourceFiles, SourceUnits, and structural relations, not Articles.
3. A repository consumer calls `search_repository` with a query and optional role/kind filters, reads returned units, and cites their commit-bound provenance.
