## Overview

Permissions are enforced at three different boundaries: caller-selected toolkit scope, user-filtered convenience tools, and model guards on Git-managed Articles. Usage tracking records which knowledge bases a conversation touched; it is not itself an authorization decision.

## Boundaries

`KBToolkit` can read only the Knowledgebase objects supplied to its constructor, and `KBSuggestToolkit` can accumulate proposals only for its single bound knowledge base. `search_user_kb` separately filters Knowledgebase rows by `owner_id` before searching Articles. The runner records each toolkit's `(knowledgebase, mode)` binding in ConversationKBUsage for provenance.

An Article backed by SourceDocument is managed content. Ordinary `save` and `delete` calls raise `PermissionError`; the source Markdown is the writable authority. `project_commit` is the narrow reconciliation path that passes `_allow_managed_write=True` while applying an allowed Git snapshot.

## Obligations

Callers must construct toolkits from knowledge bases the current principal may access; `get_bound_knowledgebases` reports scope but does not authorize it. Code using ArticleQuerySet semantic methods must apply tenant or knowledge-base filters first. Code that catches toolkit errors must not convert an authorization failure into a successful tool result. Managed-write bypasses are reserved for projection and explicit indexing paths that preserve source ownership.

## Concrete Flow

1. Application code authorizes a user and constructs `KBToolkit([allowed_kb])`.
2. The conversation runner exposes only that toolkit's schemas and records read usage for `allowed_kb`.
3. A read resolves names and Article rows inside the toolkit's bound set; `search_user_kb` uses owner filtering on its separate API path.
4. A direct edit to a Git-managed Article fails. The reviewer edits and commits Markdown instead, then `project_commit` reconciles the allowed commit atomically. Ownership conflicts are rejected rather than resolved automatically.
