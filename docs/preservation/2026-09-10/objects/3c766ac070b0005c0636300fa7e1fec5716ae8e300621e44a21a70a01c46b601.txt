## Overview

Django Ergo adds three connected planes to a Django application. The knowledge plane stores Articles and their explicitly generated embeddings. The conversation plane runs engine-backed sessions and dispatches tools. The repository plane reads an allowed Git commit, builds a searchable source-unit index, and produces review-only wiki proposals or projects committed wiki pages into Articles.

## Subsystems

### Knowledge and retrieval

`ArticleQuerySet` searches Article content and summary embeddings while preserving whatever tenant or knowledge-base filters the caller applied. `absorb_conversation` renders an existing conversation and gives an agent a read-only `KBToolkit` plus a `KBSuggestToolkit`; it returns accumulated suggestions rather than applying them.

### Conversation runtime

`Engine` defines the session, message, tool-result, and termination protocol. `SessionManager` owns engine instances for active sessions, while `run_conversation_turn` drives tool rounds, approval stops, and terminal responses.

### Repository evidence and committed projection

`search_repository` retrieves indexed `SourceUnit` records rather than Articles. `propose_repository_wiki` binds one committed goal file to observed source units and writes a non-canonical review packet. Separately, `project_commit` reconciles committed `wiki/` Markdown into Articles and tracks stable document identity through `SourceDocument`.

## Boundaries

Article retrieval and repository retrieval are different stores with different result types; neither is an alias for the other. Conversation toolkits are scoped when constructed, and their bound knowledge bases are recorded as usage metadata. Git-backed projection accepts only commits allowed by the configured source and makes managed Articles reject ordinary model writes. Wiki synthesis records proposals only; a reviewer must accept and commit a page before it can become source-controlled knowledge.

## Concrete Flow

1. A repository source is indexed at one allowed commit, producing stable source-file and source-unit records.
2. A committed wiki goal starts a conversation task with repository evidence tools and an in-memory proposal tool.
3. The task reads concrete units; `wiki_propose` rejects unobserved, too-narrow, or structurally incomplete evidence.
4. The command writes successful pages and a per-goal trace to a review packet without changing Git or Articles.
5. A reviewer corrects and commits accepted pages under `wiki/`.
6. A filesystem KB build preserves those committed pages, and `project_commit` can reconcile them into managed Articles.

## Tradeoffs

Keeping Article retrieval, repository retrieval, and Git projection separate prevents one index lifecycle from silently changing another, but callers must choose and invoke the correct indexing operation. Treating Git as authority gives reviewed pages a commit and stable provenance, but the database remains stale until an explicit projection runs. Review-only synthesis prevents an agent from publishing directly, at the cost of a required human acceptance step.
