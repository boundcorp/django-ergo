## Overview

Committed projection treats Git Markdown as the authority and the database as a derived view. `GitSnapshot` resolves a requested commit and rejects it unless it is an ancestor of the source's configured `allowed_ref`. `project_commit` parses the snapshot's `wiki/` documents, while `SourceDocument` records each page UUID, path, blob, content hash, last-seen commit, and backing Article.

## Lifecycle

1. `project_commit` captures the source checkpoint, resolves an allowed immutable snapshot, and parses every selected Markdown document before opening a write transaction.
2. A dry run returns the commit and document count without writes.
3. A real run locks the `KnowledgeSource` and rejects concurrent checkpoint movement or document UUIDs owned by another source.
4. New UUIDs create an Article and SourceDocument. Existing UUIDs update content or paths while retaining identity and prior paths.
5. Documents absent from the new tree become `missing`; they are not deleted. The source checkpoint advances only after reconciliation completes.

## Recovery

Parsing, ownership, and concurrent-update failures raise before the checkpoint advances. Database changes are enclosed in one transaction, so a failed projection does not expose a partial tree. A missing document can return under the same UUID: reconciliation reuses its SourceDocument and Article and marks it active again. Recovery is an explicit caller retry against an allowed commit; this layer does not schedule retries.

## Tradeoffs

Stable UUID identity makes renames distinct from delete-and-create and preserves provenance, but each page must maintain valid frontmatter. Marking absent documents missing preserves retrieval history and permits restoration, but callers must filter visibility rather than assuming absence means deletion. Git review remains the publication boundary; database content can lag until `project_commit` runs.
