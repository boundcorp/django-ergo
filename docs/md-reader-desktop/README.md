# Desktop Markdown reader follow-up

The coordinator verified the live **before** in a production conversation: the existing reader was flush to the top-left, occupied roughly 42% of the viewport width and 78% of its height, and dimmed chat. No production change was made or candidate tested there.

The images here use synthetic session and attachment data in the actual local App shell and Chat, not authenticated end-to-end traffic. The [desktop before](before/desktop.png) and [mobile before](before/mobile.png) use 1440×900 and 390×844 CSS-pixel viewports. The candidate after is shown at [1440×900](after/desktop.png), [1920×1080](after/wide.png), and [390×844](after/mobile.png). On desktop the dialog covers the viewport, the document has its own scroll area and centered line length, and the header retains its title, return and actions. The same native dialog, mobile dimensions and mobile rules remain in place. At 390×844 the after dialog measured 375×829 CSS pixels with 15px content padding and 11.25px corners, matching the visible before geometry; the after image shows the keyboard focus ring on Close.

## Verification and limits

- The Chat browser harness exercises desktop, wide and mobile geometry, duplicate fragments, unsupported and external links, Escape, repeated open/close, chat update, scroll and draft preservation. It uses synthetic data and mounts Chat without the App shell.
- The separate local App-shell smoke used synthetic API responses; at 1440×900 the dialog measured 1440×900 and centered Markdown measured 780px. Escape restored opener focus, chat scroll and unsent draft. A synthetic oversized response with a 500,001-byte Content-Length aborted its fetch signal and retained the download link.
- The reader browser harness checks clipboard text, download URL, image and script blocking, focus, error handling, and horizontal table/code scrolling. Component tests cover delayed oversized-response cancellation and stream limits; frontend suite and build also passed.
- Browser Back is **not** intercepted: the local App-shell smoke navigated from the open reader to the preceding route and unmounted chat. Close/Return to chat or Escape preserves the mounted chat. A component-local raw History API entry would bypass React Router's navigation bookkeeping and can leave stale entries on forward, route changes, or unmount; safely changing that contract requires coordinated router-level handling, outside this reader-only change. No navigation trap was introduced.
- The local browser uses Chromium viewport emulation. It does not prove actual device behavior, screen-reader behavior, authenticated download or permissions, or a deployed after state. Existing attachment security and server access-control behavior were not changed.
