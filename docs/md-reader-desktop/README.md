## Verification and limits

- `MD_READER_OUTPUT=/tmp/md-reader-chat-check python ergonaut/frontend/md-reader-harness/check_chat.py` passed at desktop, wide and mobile sizes against isolated local Vite servers: duplicate fragments, unsupported and external links, Escape, repeated open/close, chat update, scroll and draft preservation. It mounts Chat without the App shell.
- `python ergonaut/frontend/md-reader-harness/check_app.py` passed against the actual local App shell and Chat with synthetic API responses at 1440×900, 1920×1080 and 390×844. At desktop sizes the reader filled the viewport and the Markdown column measured 780px; Escape restored opener focus, chat scroll, unsent draft and the unchanged host query and fragment. The harness captures top and scrolled views. The earlier local App-shell smoke also checked a synthetic oversized response with a 500,001-byte Content-Length, which aborted its fetch signal and retained the download link.
- `MD_READER_OUTPUT=/tmp/md-reader-check python ergonaut/frontend/md-reader-harness/check.py` passed desktop and mobile clipboard text, download URL, image and script blocking, focus, error handling, and horizontal table/code scrolling. `bun test src/components/MarkdownAttachment.test.tsx src/components/Markdown.test.tsx` passed 11 tests; `bun test src` passed 357 tests with React `act` warnings, and `npm run build` passed with a large-chunk warning.
- The harnesses use a free local port and terminate their own Vite process group. A previous fixed-port Chat run accidentally reached an already-running baseline Vite server; that failed geometry check was discarded and all three harnesses were rerun using isolated servers.
- Browser Back is **not** intercepted: the local App-shell smoke navigated from the open reader to the preceding route and unmounted chat. Close/Return to chat or Escape preserves the mounted chat. A component-local raw History API entry would bypass React Router's navigation bookkeeping and can leave stale entries on forward, route changes, or unmount; safely changing that contract requires coordinated router-level handling, outside this reader-only change. No navigation trap was introduced.
- The local browser uses Chromium viewport emulation. It does not prove actual device behavior, screen-reader behavior, authenticated download or permissions, or a deployed after state. Existing attachment security and server access-control behavior were not changed.

## Proposed Back integration (not implemented)

The reader currently belongs to each attachment component. A local history marker keyed to a mount can go stale when Chat unmounts, while one keyed only by attachment ID cannot distinguish repeated copies of an attachment. Use a single owner inside `BrowserRouter` at the App level, with the attachment requesting a reader by ID, label and opener; leave Chat and voice ownership unchanged. The owner would render one portal and use React Router location/navigation for a desktop-only history entry, preserving the pathname, search, hash and compatible existing state. It must handle incompatible or conflicting location state without losing it.

For an entry created by the owner, Back or Escape/Return would dismiss without unmounting Chat; Forward would reopen the same reader, and reopening after Back would replace the Forward branch through ordinary router navigation. A route change would dismiss the current portal; returning to a marked history entry needs an explicit restoration policy rather than a stale component marker. Reload/direct-entry handling, safe close without assuming an owned predecessor, and focus fallback when the original opener is gone require design and regression coverage before implementation. Browser history cannot delete arbitrary older entries.

Verify with a genuine BrowserRouter stack: prior route → chat with existing state/query/hash → reader, Back/Forward and repeated close/reopen; duplicate attachment cards; route navigation while open and return; reload/direct entry; existing fragment links, draft, transcript scroll and focus; mobile without added entries; and voice navigation. No such routing change or history regression assertion is included in this follow-up.
