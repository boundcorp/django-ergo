# Realtime voice progress

## Current branch

The off-by-default prototype uses Django-owned logical sessions, finalized events, bounded extractive compact state and reported-activity anchors, stable delegation IDs, a durable completion outbox, a single chat card per voice session and a minimal Stage. User speech times supplied by a client are separate and have unknown clock error. Elapsed time is calculated since server receipt of the user's report, not since a verified physical action. The rules are not a semantic summarizer; unmatched statements can fall outside the bounded transcript window. The model's actual live use of silent time context remains unverified.

Browser callers can create, read, end and obtain room-scoped microphone-only tokens for their own voice sessions, but cannot write events, state or delegations. Background delegation is off unless `REALTIME_VOICE_DELEGATION_BUDGET` is set. A delegation is a thread message that carries that budget, and the turn runner enforces it server-side: model turns, input and output tokens, a wall-clock deadline, an allowlist of read-only tools, no worker, agent or background-task starts, no thread sends, no retries, no approvals. A limit ends the turn as a truthful failed result that the same voice session receives through the durable outbox; a turn without a budget is unchanged. A locked durable claim allows at most one commentary attempt per result across connections; a crash after claim may lose that announcement, but the linked result remains visible. The claim is not evidence of playback or hearing. The inspected GPT-Live adapter's `append_commentary` returns no speech identifier for correlating an announcement to browser playback. Model behavior on restored context is not deterministic.

## Remaining gates and rollout

No live audio, browser playback acknowledgment, real delegated model result, provider billing or measurement of how conservative the input estimator is has been demonstrated. The [full-stack planning proposal](realtime-voice.md#livekit-and-conservative-planning) reserves $0.15 plus taxes for one attempt only under its stated assumptions, not a guaranteed or enforceable spend ceiling. LiveKit's free Build plan has a hard allowance, but the shared project's current plan and remaining allowance remain unverified.

Before a paid test: explicitly approve use of the shared project and the conditional reserve; confirm Build plan and sufficient **shared** remaining participant-minutes and downstream bandwidth, and establish that no external worker will take the unique dispatch. Check the worker, local web server and isolated routes are still the ones above, the queue is empty and the fresh test chat is selected. Confirm `record=False` remains in the runner and no optional paid services are enabled; check provider billing can be monitored and the runtime key still passes the read-only metadata checks. Hosted inference entitlement, browser microphone/playback and actual billing remain unknown until an approved attempt.

No documented read-only API for the shared remaining Build allowance was found: the Cloud API requires a separate user session and its documented project object has no plan or remaining-allowance fields. On the project's **Billing** dashboard (`https://cloud.livekit.io/projects/<project-id>/billing`), inspect plan and current-cycle WebRTC participant-minutes and downstream data usage. The exact dashboard remaining-allowance field was not observed; because Build quotas are shared across the user's free projects, project-level usage alone may not establish the remainder. Resolve that before approval, including with LiveKit support if necessary.

A one-shot bridge cap and outer timeout are not hard provider-billing limits. Before any shared rollout: separately review migration and retention, compare reported usage with the estimator, measure live behavior and billing, then separately approve deployment and migration. Rollback stops only the isolated processes; persisted history and already queued work require explicit handling.
